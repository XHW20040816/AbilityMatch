## 3. 各章写作要点

### 第 1 章 绪论

- 用“三个断裂”组织背景：规划断裂（低年级）、材料断裂（高年级）、信息断裂（企业简章）。
- 现状部分不要泛泛而谈，落到“现有招聘 App 只做信息聚合，不做能力结构化比对；校园系统只做记录，不做成长引导”。
- 明确本文工作：单机、无后端、词典与规则内置、五维加权匹配。

### 第 2 章 相关技术

- 只写用到的：Stage 模型（UIAbility 生命周期）、ArkTS 的强类型与状态装饰器（`@State`）、ArkUI 声明式布局、`relationalStore`、`Preferences`、`cameraPicker`/`photoAccessHelper`、`reminderAgentManager`、`DocumentViewPicker`。
- 每个技术点用一句话说明“为什么选它”，避免变成官方文档抄录。

### 第 3 章 需求分析

- 角色不要写成“两个 App”，要强调“同一学生的两个成长阶段视图 + 企业视角”。
- 19 条 FR 用表格呈现，标注优先级，与第 5 章实现一一对应（评审常查这条链）。

### 第 4 章 系统设计

- 架构图必须体现“无后端”：表现层 → ViewModel → Service → Repository → RDB/Preferences/沙盒文件。
- 数据库章要写清“为什么比题目多 2 张表”：`skill_certificate` 与 `project_experience` 是为“能力画像”提供结构化输入，避免把证书信息塞进备注字段。
- 算法章是加分项，写清三件事：
  1. 归一化：别名 → 词典标准名（`TextMatcher.canonicalList`），英文按词边界匹配避免 Java 命中 JavaScript；
  2. 五维加权：`总分 = Σ(维度分 × 权重) / Σ权重`，权重由企业侧 Slider 配置；
  3. 差距与建议：仅对“岗位要求但学生缺失”的项生成 gap，再按 `advice_lib` 匹配建议。

### 第 5 章 系统实现

- 按“页面 → 服务 → 数据”的顺序写，每节配 1 张截图 + 1 段关键代码（不超过 15 行）。
- 图片管理单独一节：拍照/选图 → 复制进 `filesDir/certs/` → 库里只存相对路径 → 删除记录时同步 unlink。
- 检索优化单独一节：`search_text` 冗余字段 + `LIKE` + 组合索引 `(student_id, honor_type, level, award_year)` + 分页 `LIMIT/OFFSET`。

### 第 6 章 系统测试

- 先写环境表，再写“构建 → 单元 → 功能 → 性能”四段。
- 数字必须与 `05` 一致：33 任务 / 39.6 s / 3.21 MB / 9 用例 / 40.45% / 24 条功能用例。
- 性能段若仍未补测，写明“测试方案已设计，数据待补”，不要编造耗时。

### 第 7 章 总结与展望

- 完成度用“57 项要求：52 完全、4 基本、1 未完成（论文本身除外则为 52/4/0）”表述，主动暴露短板比藏着更好。
- 展望三条即可：接入 OCR 自动识别奖状文字、成长方向模板可在线扩展、匹配记录保留历史并支持趋势图。

## 4. 答辩 PPT 结构（10～12 页）

1. 封面（题目、姓名、学号、指导教师）
2. 研究背景与问题（三个断裂）
3. 需求分析（角色 + 用例图）
4. 技术方案（Stage + ArkTS + RDB + Preferences，强调无后端）
5. 系统架构图
6. 数据库设计（ER 图 + 9 表）
7. 核心算法（归一化 + 五维加权 + 差距建议）
8. 功能演示（截图 4～6 张，证书归档与画像为重点）
9. 测试结果（构建 + 单元 + 覆盖率 + 功能用例）
10. 不足与展望
11. 致谢 / Q&A
